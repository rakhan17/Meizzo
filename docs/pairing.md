# Pairing

## User flow

Client registers a six-digit offer with an expiry and approval flag. Controller
submits the code. The backend forwards a request to the Client, which must
approve explicitly. On approval, the backend issues one Client token and one
Controller token, sends each only to its intended peer, and consumes the code.

## Protocol messages

The implemented message names are:

| Direction | Message |
|---|---|
| Client to backend | `client.register_pairing_offer` |
| Controller to backend | `controller.request_pairing` |
| Backend to Client | `client.pairing_request` |
| Client to backend | `client.pairing_decision` |
| Backend to both | `client.pairing_completed`, `controller.pairing_result` |
| Either to backend | `auth.connect` |
| Either to backend | `heartbeat` |

Pairing attempts are rate-limited per Controller ID. Offers expire after at
most ten minutes. The service keeps state in memory; a restart invalidates
offers and active authorizations.

## Security properties

Tokens are random values generated by the backend and are not logged. The
backend checks the role, token, Client ID, and Controller authorization before
routing commands or snapshots. A Controller authenticated for Client A cannot
route a command to Client B.
